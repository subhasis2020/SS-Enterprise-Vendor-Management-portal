Snapshot as of 2026-09-29, end of a session that took the app from "never deployed" to live on bigmartsingur.in via Plesk shared hosting, plus a rework of the Sales page. See [[ss-portal-overview]] for stack/workflow and [[deploy-workflow]] for the publish/Desktop-bigmart routine — always apply that routine when this project's files change.

**Deployment**: bigmartsingur.in is on Plesk shared hosting (Windows/IIS, no SSH). Fixed along the way: missing `ConnectionStrings__bigmartconn` env var (app was crashing on start, HTTP 500.30) — set via `web.config`'s `<environmentVariables>` since Plesk's panel didn't expose one; and the host's IIS hard-blocks the `PUT` verb (plain IIS 403, before the app ever sees the request) — fixed by moving every edit/update endpoint to `POST .../edit` instead of `MapPut` (see [[deploy-workflow]] for the "always POST" rule going forward).

**Nav**: now Dashboard, Sales, Sales by month, Vendor payments, Cheque details, Expenses, Products, To-do (Sales/Sales by month/Products/To-do were all re-enabled or added this session — see [[ss-portal-overview]]). Monthly profit, Customer credit, Product sync remain unlinked by request.

**Vendor payments** (`#/vendors`): added a "+ Vendor" button/modal (`POST /api/vendors`) to create a new supplier, then jumps straight to its detail page. Edit vendor / edit invoice / edit payment all now go through `POST .../edit` (not `PUT`) per the hosting fix above — same validation/DB writes as before, only the verb and URL suffix changed. There is no actual role/admin restriction anywhere on these — confirmed by reading the code; if "needs an admin account" ever reappears, it's the generic client-side 403 handler misfiring, not a real permission check.

**Sales by month** (`#/trend`): the 4 stat chips (total sale/bills/avg/best month) were removed per request — only the Range picker, Export CSV, chart, and table remain. Table now lists most-recent-month-first (reversed for display only); the bar chart stays chronological left-to-right (normal trend-chart convention) and the "vs prev month" calc still uses the original chronological order internally.

**Sales** (`#/sales`, reworked significantly this session):
- Filter is now a single **Date** field (default: today), not a From/To range. Changing it re-renders the table for that day.
- Bill-ID search box ignores whatever date is selected and searches the *entire* table by SaleID prefix (backend: `SalesEndpoints.cs` nulls out the date filter whenever a search term is present).
- Export CSV, the 4 stat chips, and the "Before tax" column are all removed from the list.
- **Price mismatch flagging**: `TB_SaleProduct` has both `ActualSalePrice` (what was actually charged) and `POSSalePrice` (the POS-listed price — confirmed with the user this is the one that reflects what's "actually charging to customer", so it's what's displayed as "POS price"/used for `Line total`, not `ActualSalePrice`). Any line item where `ActualSalePrice != POSSalePrice` gets a red-tinted row (`.flag` CSS class) in both the bill-detail modal and, if any item in a bill mismatches, that bill's row in the main Sales list too. The list-level flag is `PriceMismatch`, computed via a single joined derived-table aggregate over `TB_SaleProduct` (not a per-row correlated subquery — that table has no index on `SaleID`, confirmed via [[ss-portal-overview]]'s "never assume a column/index exists" note, so a per-row subquery would've been expensive).
- Bill-detail modal: **no cost/profit shown at all** (explicit request — the old "Cost" column and "gross profit" chip are gone). Instead shows per line item: POS price, Actual price, Diff (Actual − POS), Diff %. Two summary chips at the bottom: "bill total" (from `TB_Sale.TotalSale`) and "total difference" (Σ `(ActualSalePrice − POSSalePrice) × Quantity` across all items).

**Dashboard** (`#/dashboard`) order: KPI grid → **To-do card** (only rendered at all if there are open tasks — hidden entirely otherwise; top 8 open tasks, checkbox on the right of each row, clicking it opens a confirm popup ("Mark ... as done/not done?") before actually toggling, blinking red dot next to any task due today, "+ Task" button, "View all tasks" link to `#/todos`) → Vendor activity card → Last cheques → Daily sales (current month) → **Vendor payments by month** bar chart (year dropdown top-right, same placement pattern as the Vendor activity date picker; bars show the ₹ amount directly above them via a small custom Chart.js plugin `barValueLabels`, since no datalabels plugin is loaded).

**To-do** (`#/todos`, new page + nav item, added 2026-09-29): full CRUD against a **new DB table `TB_Todo`** (ID, Title, Notes, DueDate, IsDone, CreatedDate, CreatedBy, CompletedDate — created this session, wasn't there before). Backend `TodoEndpoints.cs`, all mutations are `POST` (`/api/todos`, `/api/todos/{id}/edit`, `/api/todos/{id}/toggle`, `/api/todos/{id}/delete`) per the no-PUT/DELETE hosting rule in [[deploy-workflow]]. Checkbox toggle is on the right of each row and always goes through a confirm popup (`confirmModal` helper in `app.js`, reusable) before applying. Any task whose `DueDate` equals today gets a blinking red dot (`.blink-dot` CSS class, `@keyframes blinkDot`, 13px). User said "my account will add task for me" — i.e. tasks can also be inserted programmatically (by Claude, in a future session) via the API/DB directly, not just through the UI.

**Products** (`#/products`, added 2026-09-29, took over the route that used to be the flat "Product report" list): now an insights/analytics landing page — KPI row (total products, low stock count, out-of-stock count, slow-moving count, stock value at cost), a "Top sellers" horizontal bar chart (last 30 days, by revenue at POS price), a "Low stock" table (1–5 units, sorted lowest-first), a "Slow moving" table (in stock but zero sales in 60 days, sorted by ₹ tied up in stock descending — the most actionable list), and an "Out of stock" table (sorted by all-time `product_sold` so the historically-popular OOS items surface first). Backend: `GET /api/products/insights` in `ProductEndpoints.cs`, one `QueryMultipleAsync` round trip using **temp tables** (`#recent30`/`#recent60`, not CTEs — CTEs don't survive across multiple statements in one batch, temp tables do) so the `TB_SaleProduct`⋈`TB_Sale` join for the 30/60-day windows is computed once and reused across all 5 result sets. The old flat/filterable product list still exists, moved to `#/products/all` (linked from the bottom of the insights page as "View full product report →"), same sub-route pattern as `#/vendors/{id}` and `#/trend/{month}`.


**2026-10-01 session additions** (all published to `Desktopigmart`, `ASSET_V` now `2026100109`):

Vendor edit-payment modal already had Notes (user was probably on a stale upload).

To-do red blink = open task due today **or overdue**.
